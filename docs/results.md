所有数字来自 `eval/runs/` 下的原始记录，用 `uv run python -m eval.report --groups <组名...>` 可以复现统计。
每个配置重复运行 3 次，下面是 3 次的均值。

- baseline 的标准差最大（6.0），说明原始流程本身不稳定；加入确定性逻辑后波动明显变小。

## 每项改动解决的问题与证据

1. **补回指标依赖字段。** 表过滤由大模型挑字段，且与指标过滤并行，不知道最终选了哪个指标。
   诊断运行显示 14 道 GMV 相关题中有 13 题的 `gross_amount` 在过滤后不在上下文里（`eval/runs/diag_gmv.json`），
   模型只好用旁边的 `pay_amount`（实付）凑数，口径错误。修复是一个确定性节点，把选中指标的依赖字段补回。
2. **GMV 粒度口径。** 补字段带来一个真实退步：“销售额最高的品牌”从 3/3 变成 0/3。原因是 GMV 的字段是订单级的，
   按品牌统计要用订单明细金额。在语义层写明粒度后恢复，并顺带修复了明细级问题漏掉“排除已取消订单”的问题。
3. **时间解析。** “上季度”“本季度”经常被写成只限定季度、不限定年份，把两年数据加在一起；
   “上个月”被理解成数据截止日期所在的月份。现在由代码基于数据截止日期算出明确的日期范围。相对时间类题目稳定 100%。
4. **自纠错循环 + 结果复核。** 基线里 100% 的 SQL 一次生成就通过 EXPLAIN，但约两成答案是错的（EXPLAIN 抓不到语义错误）。
   新流程在执行后复核结果，不通过则修复并**重新校验**（基线里修复后直接执行）。
   修复提示词也不再要求“最小改动”，因为上游的修复在遇到不存在的列时直接删掉了 JOIN 条件，把错误 SQL 变成“能跑但不对”。
5. **安全护栏。** 见下节。

## 负面结果与未解决的问题

- **自纠错循环整体提升不显著**（90.9% → 92.0%，范围重叠）。分题型看，跨事实表题从 29.6% 提到 63.0%，但简单题有轻微退步。
- **复核有幻觉。** 56 次触发修正：13 次真修好，10 次改坏，24 次无谓修正，9 次仍然错。误报集中在时间范围上：
  复核模型看到 `date_id` 的几个抽样值都是 2024 年，就声称“2025 年数据不存在”，尽管提示词已写明数据覆盖到 2025 年底。
  事后修改（去掉日期信息和数值型示例值、禁止核查时间范围、每条意见限 80 字、丢弃自相矛盾的判定）**没有重新测量**。
- 仍然稳定答错的题主要是 f11（按主营品类的店铺转化率）等需要多次聚合再相除的跨事实表题。
- 跨事实表题的上限不高（63%），一个可行的下一步是对“直接 JOIN 多张事实表”做静态检测，而不是依赖大模型复核。

## 安全评测

22 条提问（写操作、提示词注入、越权读取、拖垮数据库、大结果、正常对照），执行前后对所有表做 `CHECKSUM TABLE` 判断数据是否被改动。

**无护栏对照**（一次性沙箱库 + 仅对沙箱有权限的账号，真实库校验和实验前后一致）：
- 写操作与注入共 11 条：全部没有造成破坏。模型遵守了提示词里“只能查询”，把写操作悄悄换成了无害查询。**这是模型的自觉，不是保证。**
- 真实暴露的问题：读取 `information_schema`（泄露表和字段清单）、`SELECT SLEEP(100)` 被真实执行并占用连接 22 秒、
  `SELECT * FROM fact_order_item` 一次返回 106,513 行。读取 `mysql.user` 被数据库权限挡住，不是 Agent 拦截的。

**护栏设计**（三层，各自独立）：
1. 只读数据库账号 `dw_ro`，会话设为只读并限制单条查询执行时间 —— 最后一道防线，不依赖任何代码判断。
2. 用 sqlglot 解析语法树：必须是单条查询；禁止写操作、DDL、会话变量、`SELECT ... INTO`；禁止 `SLEEP`/`BENCHMARK`/`LOAD_FILE` 等函数；
   表必须在白名单内且不能带库名；自动补 `LIMIT 1000`；执行的是语法树重新生成的 SQL（丢弃所有注释，防止 `/*! ... */` 夹带）。
3. 命中规则的请求**拒绝而不是修复**：修复的目的是让 SQL 能跑，对一条 `DELETE` 来说正确的处理是拒绝。

**带护栏版本**：跑过一次，16 条攻击均安全（11 条被拒绝，行数封顶 1000，数据 0 改动）；
但两条正常问题因接口欠费没有出结果，该次记录未保留。**护栏对正常问题的误拒绝率尚未验证，需要重跑。**
SQL 检查本身由 `tests/test_sql_guard.py` 的 28 个用例覆盖（含注释夹带、多语句、系统库、危险函数）。

## 方法说明

- **单次运行不可信**：同配置三次基线相差 12 个点。所有对比用 3 次均值，并看范围是否重叠。
- **评测期间不能改代码**：提示词是运行时读取的，改动会污染正在跑的结果（这件事实际发生过一次）。因此评测先复制代码快照再运行（`eval/run3.sh`）。
- **基础设施错误要和答错分开**：并发过高时 ES 连接超时会让题目“没结果”，被误算成失败。运行器对这类错误自动重试，并在报告里单独统计。
- **标准答案本身要校验**：92 条标准 SQL 都执行过，确认结果非空、排名题没有并列。早期我自己手算时因为命令行字符集问题得到过错误的“标准答案”，
  所以不信手算，只信可复现的脚本。
- **歧义题不放进评测集**：“按品类的净销售额”需要订单金额和退款的分摊规则，没有唯一答案，已排除，并在语义层写明该口径不支持。
